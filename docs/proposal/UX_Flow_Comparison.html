Kraftworks Career Hub — UX Flow Comparison

Current Codebase (Supabase) vs. Proposed Architecture (Clerk + Cloudflare + OpenRouter + Resend)

Companion document to the Kraftworks Backend Proposal PRD. Compares every user-facing flow between the existing implementation and the proposed backend migration.

1. Document Purpose

This document walks through every user journey in the Kraftworks Career Hub — from first visit to AI-assisted career feedback — and compares the current experience (built on Supabase) with the proposed experience (built on Clerk, Cloudflare Workers/D1, OpenRouter, and Resend). The comparison is flow-by-flow, identifying what changes, what stays the same, and why the change matters for the user.

Key principle: The frontend React application and UI components remain unchanged. The user sees the same pages, the same buttons, and the same visual design. What changes is what happens after the user clicks — the authentication mechanism, the API endpoints, the data layer, and the AI inference pipeline. This document makes those invisible changes visible.

3. Flow 1 — New User Registration and Onboarding

3.1 Current Flow (Supabase Auth)

1
User navigates to /auth

Lands on a custom-built React form with email, password, and full name fields. Toggle between "Sign In" and "Create Account" modes via text link.

2
User submits signup form

React calls supabase.auth.signUp({ email, password, options: { data: { full_name } } }). The full name is stored in Supabase's raw_user_meta_data JSON field on the auth user record.

3
Email confirmation

Supabase sends a confirmation email via its built-in email service (limited to 4 emails/hour on free tier). User must click the confirmation link before the account is active.

4
Session established

After confirmation, the Supabase client stores a JWT and refresh token in localStorage. The useAuth hook detects the session via supabase.auth.onAuthStateChange listener. User is redirected to /dashboard.

5
Dashboard loads

Dashboard fetches resume status, AI usage count, and latest feedback/questions from Supabase PostgreSQL via the Supabase client SDK. Row-level security (RLS) policies ensure users can only read their own data.

3.2 Proposed Flow (Clerk)

1
User navigates to /auth

Lands on the same route, but the custom form is replaced by Clerk's pre-built <SignIn /> and <SignUp /> components. These are fully styled React components that handle email/password, social OAuth (Google, GitHub), and magic link authentication out of the box. The visual design is customised via Clerk's theming API to match Kraftworks branding.

2
User submits signup

Clerk handles the entire signup flow — form validation, password strength enforcement, email verification — without custom code. The full name is captured as a Clerk user attribute. Clerk creates a user record in its managed user store and issues a session JWT.

3
Email verification

Clerk sends a verification email via its production email infrastructure (no rate limits like Supabase's 4/hour free tier). Verification can be a magic link or a 6-digit OTP code — configurable in the Clerk dashboard.

4
Clerk webhook fires

When the user is created, Clerk fires a user.created webhook to a Cloudflare Worker endpoint. The Worker creates a corresponding record in the D1 users table, syncing the Clerk user ID, email, and full name for local queries. This is a backend synchronisation step — invisible to the user.

5
Session established

Clerk's React SDK (@clerk/clerk-react) manages the session automatically. The useAuth hook is refactored to use useUser() and useAuth() from Clerk's SDK instead of Supabase's onAuthStateChange. The user is redirected to /dashboard.

6
Dashboard loads

Dashboard calls Cloudflare Worker API endpoints (instead of Supabase client SDK) with the Clerk session JWT in the Authorization header. Workers query D1 for resume status, AI usage, and feedback data. Access control is enforced at the Worker level by verifying the Clerk JWT — not via database-level RLS policies.

What Changes for the User

  • Visual: The login/signup form changes from a custom-built React form to Clerk's pre-built components. The layout is similar but more polished — includes social login buttons, better password strength indicators, and a smoother verification flow.
  • Functional: Social login (Google, GitHub) becomes available without custom OAuth integration. Magic link login is an option. Email verification is more reliable (no 4/hour rate limit).
  • Perceived speed: Dashboard data loading latency may change slightly because data now comes from Worker → D1 instead of Supabase client SDK → PostgreSQL. In practice, the difference is negligible or faster (D1 is at the edge).

4. Flow 2 — Resume Upload and AI Feedback

This is the core value flow of the platform. A trade graduate uploads their resume, receives AI-generated feedback, and the feedback is reviewed by an admin before the user sees it.

4.1 Current Flow (Supabase + Lovable AI Gateway)

1
User navigates to /resume-review

Protected route — ProtectedRoute component checks useAuth for active Supabase session. If no session, redirects to /auth.

2
User uploads a PDF resume

The useResume hook handles file upload. The PDF is uploaded to Supabase Storage at path resumes/{user_id}/{filename}. A SHA-256 hash of the file content is computed client-side. A record is inserted into the resumes table with file metadata (file_name, file_path, file_size, file_hash, trade_program).

3
User clicks "Get Resume Feedback"

The useResumeFeedback hook first calls canRunAI() from useAIUsage to check if the user has remaining quota. If quota is exhausted, the button is disabled and a message is shown.

4
Edge function invocation

The hook calls supabase.functions.invoke('generate-resume-feedback', { body: { resume_id } }). The Supabase Edge Function (Deno runtime) receives the request, verifies the caller's JWT, checks quota in PostgreSQL, fetches resume metadata, builds the prompt, and calls the Lovable AI Gateway with model gemini-2.5-flash-lite.

5
AI response processing

The edge function parses the tool-call JSON from the Gemini response. It extracts overall_score, strengths, improvements, suggestions, trade_suggestions, and actionable_steps. The function returns this data to the client.

6
Client-side persistence

The useResumeFeedback hook receives the AI response and inserts the feedback record client-side via supabase.from('resume_feedback').insert(...) with status: 'pending_review'. The hook also calls recordAIUsage() to insert an AI usage record. Note: the persistence happens on the client, not in the edge function.

7
Admin notification (stub)

The edge function fires a request to notify-admin-resume as a fire-and-forget call. This function currently returns immediately with a stub response — no actual email is sent. Admins must check the admin panel manually to discover new feedback submissions.

8
User sees "Pending Review" state

The dashboard and Resume Review page show the feedback status as "Pending Review" with a clock icon. The user cannot see the AI-generated content until an admin approves it.

4.2 Proposed Flow (Clerk + Cloudflare Workers + D1 + OpenRouter + Resend)

1
User navigates to /resume-review

Protected route — Clerk's <SignedIn /> / <SignedOut /> components or the useAuth() hook (from Clerk SDK) gates access. Functionally identical to the user.

2
User uploads a PDF resume

The useResume hook is refactored to upload the PDF to a Cloudflare Worker endpoint instead of Supabase Storage. The Worker stores the file in Cloudflare R2 at key resumes/{clerk_user_id}/{filename} and inserts the resume record into D1. SHA-256 hash is still computed client-side and sent with the upload.

3
User clicks "Get Resume Feedback"

Same UX — the button is disabled if quota is exhausted. The quota check is now performed by calling a Worker endpoint that queries D1 instead of querying Supabase PostgreSQL directly from the client.

4
Worker receives request, dispatches Workflow

The client sends a POST to the generate-resume-feedback Worker with the Clerk JWT and resume_id. The Worker verifies the JWT using Clerk's JWKS, then dispatches a Cloudflare Workflow — a durable, multi-step execution sequence. The Worker returns immediately with a 202 Accepted or waits for workflow completion (configurable).

5
Workflow executes 6 durable steps

Step 1: Validate ownership, quota, deduplication against D1. Step 2: Fetch resume metadata and trade context from D1. Step 3: Send structured prompt to OpenRouter (model: google/gemini-2.5-flash) with forced tool-call schema. Step 4: Normalise the AI response (clamp score, validate arrays). Step 5: Write feedback + usage records to D1 in a single transaction. Step 6: Send admin notification email via Resend.

6
Persistence is server-side

Unlike the current system where the client inserts the feedback record, persistence now happens entirely within the Cloudflare Workflow. The client receives a response only after the feedback is durably stored. This eliminates the race condition where the client could fail to persist after a successful AI call.

7
Admin receives real email

Resend delivers a production-grade transactional email to the admin with user details, trade program, and a direct link to the admin panel. This replaces the current stub notification. Admins no longer need to manually check the panel — they are proactively notified.

8
User sees "Pending Review" state

Identical to current UX. The user sees the same pending state, same clock icon, same messaging. The admin approval gate is unchanged.

What Changes for the User

  • Visual: Nothing changes. The page looks identical.
  • Functional: The AI model switches from Gemini 2.5 Flash Lite (via Lovable Gateway) to Gemini 2.5 Flash (via OpenRouter) — slightly higher quality output. Feedback quality may improve due to better model and improved prompt engineering.
  • Reliability: Significantly improved. The current flow has a single-point-of-failure: if the client crashes after the AI call but before the database insert, the user loses their quota with no feedback saved. The proposed Workflow eliminates this — persistence is server-side and durable.
  • Admin experience: Admins now receive email notifications instead of having to poll the admin panel. This reduces the time between submission and review.

5. Flow 3 — Interview Question Generation

5.1 Current Flow

1
User navigates to /interview-prep

Protected route. Page displays a textarea for the job description, a note about resume being required, and the remaining AI action count.

2
User pastes job description and clicks "Generate Questions"

Client validates that a resume exists (required for context) and that quota is available.

3
Edge function processes

The generate-questions Supabase Edge Function validates the job description (min 10 chars, max 2000), fetches resume context, checks quota, builds the prompt, and calls Lovable AI Gateway with model gemini-3-flash-preview. The function computes a SHA-256 hash for deduplication and persists the question set to interview_questions server-side.

4
Questions returned immediately

Unlike resume feedback, questions are returned directly to the user without admin review. The page displays three categorised sections: Technical, Behavioural, and Situational questions.

5.2 Proposed Flow

1
User navigates to /interview-prep

Same protected route, now gated by Clerk session instead of Supabase session. Interface identical.

2
User pastes job description and clicks "Generate Questions"

Same client-side validation. Request sent to Cloudflare Worker with Clerk JWT.

3
Worker dispatches interview question Workflow

5-step durable Workflow: validate → enrich context → call OpenRouter (google/gemini-2.5-flash) with Bloom's-aligned prompt → normalise + persist to D1 → return questions. Each step retries independently on failure.

4
Questions returned immediately

Same immediate delivery. No admin review gate. Interface shows the same three-category layout.

What Changes for the User

  • Visual: Nothing. Same page, same categories, same question display.
  • Functional: AI model changes from gemini-3-flash-preview (preview quality, potentially unstable) to google/gemini-2.5-flash (production model via OpenRouter). Question prompts are now explicitly aligned to Bloom's Taxonomy levels, which may produce more systematically varied questions.
  • Reliability: Improved. If the AI call succeeds but the database write fails, the Workflow retries only the write — the user always gets their questions without burning an extra AI call.

6. Flow 4 — Admin Review Workflow

6.1 Current Flow

1
Admin navigates to /admin

The useAdminRole hook queries the user_roles table in Supabase PostgreSQL to check if the current user has the 'admin' role. If not, the page shows an access denied message.

2
Admin views pending feedback

The "Resume Feedback" tab fetches all records from resume_feedback ordered by creation date. Each record shows the user's email, trade program, score, status badge, and action buttons. Admins must manually navigate to this panel to discover new submissions — there is no email notification.

3
Admin approves, edits, or rejects

Clicking a status button updates the status field in resume_feedback via a direct Supabase client update. The admin can also edit feedback fields (score, strengths, improvements) in a dialog. All operations are direct client-to-database writes — no server-side validation.

4
User sees approved feedback

Once the status changes to 'approved', the user's next Dashboard or Resume Review page load fetches the updated record. The feedback (score, strengths, improvements, trade suggestions) is now visible.

6.2 Proposed Flow

1
Admin receives Resend email notification

When a user generates resume feedback, the Workflow sends a transactional email to the admin with: user name, trade program, resume filename, submission time, and a direct link to /admin?tab=feedback&id={feedback_id}. The admin is proactively notified instead of having to poll.

2
Admin navigates to /admin

Role check is now performed by verifying the Clerk JWT's organisation role or by querying the D1 user_roles table via a Worker endpoint. The admin panel UI is identical.

3
Admin approves, edits, or rejects

Status updates are now sent to a Cloudflare Worker endpoint (not direct client-to-database). The Worker validates the admin's Clerk JWT and role, then updates D1. This adds server-side authorisation — in the current system, any user who knows the table structure could potentially modify feedback status directly via the Supabase client (even with RLS, this is a broader attack surface than a Worker with explicit role checks).

4
Optional: User receives email on approval

When the admin approves feedback, the Worker can trigger a Resend email to the user: "Your resume feedback is ready! Log in to view your results." This is a new capability that does not exist in the current system.

5
User sees approved feedback

Same as current — feedback becomes visible on next page load after approval.

What Changes for the User and Admin

  • Admin notification: Admins receive proactive email notifications instead of manually checking the panel. This is the single biggest operational improvement — it reduces time-to-review from "whenever the admin remembers to check" to "minutes after submission."
  • Security: Admin operations go through a Worker with explicit JWT + role verification. In the current system, admin operations are client-to-database with RLS — functional but a broader trust surface.
  • User notification (new): Users can optionally receive an email when their feedback is approved. This closes the loop — currently, users must log back in and manually check.

7. Flow 5 — Waitlist Signup (Trade Graduate and Employer)

7.1 Current Flow

1
Visitor navigates to /waitlist

Public page with two modes: "Trade Graduate" (6 fields: full name, email, trade program dropdown, state, city, consent checkbox) and "Employer" (8 fields: full name, job title, company email, trades hiring for, hiring volume, state, city, consent checkbox). Mode toggle via tab-style buttons.

2
Visitor submits form

The React component inserts directly into trade_grad_waitlist or employer_waitlist via the Supabase client SDK: supabase.from('trade_grad_waitlist').insert({...}). This is a direct client-to-database write — no server-side validation beyond Supabase column constraints.

3
Success toast

A toast notification appears: "You've been added to the waitlist!" No confirmation email is sent. No admin notification is sent.

7.2 Proposed Flow

1
Visitor navigates to /waitlist

Same page, same two modes, same fields. No visual change.

2
Visitor submits form

The React component sends the form data to a Cloudflare Worker endpoint via HTTP POST. The Worker performs server-side validation (email format, required fields, consent = true) and inserts into the appropriate D1 table. Server-side validation means malicious clients cannot bypass form rules by calling the API directly.

3
Confirmation email via Resend

The Worker sends a confirmation email to the visitor: "Thanks for joining the Kraftworks waitlist! We'll notify you when your spot is ready." This is a new capability — currently, no email is sent.

4
Admin notification email (optional)

The Worker can optionally send a summary email to the admin when new waitlist entries arrive — either individually or as a daily digest. This gives the team visibility into lead flow without checking the admin panel.

5
Success toast

Same toast as current, plus the user receives a confirmation email.

What Changes for the Visitor

  • Visual: Nothing changes on the page itself.
  • Functional: Visitors now receive a confirmation email — a professional touch that the current system lacks. Form validation is now server-side (not just client-side), which prevents abuse via direct API calls.
  • Security: Moving from client-side Supabase inserts to Worker-mediated inserts eliminates the exposure of the database write endpoint to the public internet via the Supabase client SDK.

8. Flow 6 — Dashboard Overview

8.1 Current Flow

1
Authenticated user loads /dashboard

The dashboard makes 4+ parallel queries via the Supabase client SDK:

  • useResume: Fetches the user's resume record from resumes table.
  • useAIUsage: Counts AI usage records to compute remaining quota.
  • useResumeFeedback: Fetches latest feedback record for the current resume.
  • Direct query: Fetches latest interview question set from interview_questions.
2
Dashboard renders 3 cards

Resume Card: Shows upload state (no resume / uploaded with filename). AI Actions Card: Shows usage progress bar (used/max) and remaining count. Feedback Card: Shows latest feedback status (pending/approved) and score if approved. Interview Card: Shows latest question count and generation date.

8.2 Proposed Flow

1
Authenticated user loads /dashboard

The dashboard calls a single Cloudflare Worker endpoint: GET /api/dashboard-summary with the Clerk JWT. The Worker queries D1 for resume, usage, feedback, and interview data in a single database roundtrip (D1 supports batch queries). This replaces 4 separate client-to-database roundtrips with 1 client-to-Worker request.

2
Dashboard renders same 3 cards

Identical UI. The data shape is the same — only the source changes. TanStack Query caches the response identically regardless of whether it came from Supabase or a Worker.

What Changes for the User

  • Visual: Nothing.
  • Performance: Potentially faster. 4 parallel client-to-Supabase requests are replaced by 1 client-to-Worker request that batch-queries D1 at the edge. Fewer network roundtrips = faster dashboard load, especially on slower connections.

10. Summary: Side-by-Side Comparison Table

Aspect Current (Supabase) Proposed (Clerk + Cloudflare + OpenRouter + Resend)
Authentication UI Custom React form (email + password only). Clerk pre-built components (email, social OAuth, magic link).
Session Management Supabase JWT in localStorage. onAuthStateChange listener. Clerk managed sessions. @clerk/clerk-react hooks.
Data Fetching Supabase client SDK directly queries PostgreSQL. Multiple parallel requests from client. Cloudflare Workers as API layer. Batch queries to D1. Single request for dashboard data.
AI Inference Lovable AI Gateway → Gemini Flash Lite / Gemini 3 Flash Preview. OpenRouter → model-configurable (Gemini Flash, Claude Haiku, Llama). With durable retry via Workflows.
AI Pipeline Durability Single edge function call. If it fails, the entire operation fails. Client-side persistence for resume feedback. Cloudflare Workflow with step-level durability. Server-side persistence. Individual step retry.
File Storage Supabase Storage with RLS-scoped paths. Cloudflare R2 with Worker-enforced access control.
Admin Notifications Stub function — no email sent. Admins poll manually. Resend transactional email with direct admin panel links.
User Notifications None beyond Supabase confirmation email at signup. Resend emails for: waitlist confirmation, feedback approval notification (new).
Authorisation Model PostgreSQL RLS policies + client-side user_roles query. Clerk JWT verification + Worker middleware role checks against D1. No direct client-to-database access.
Waitlist Forms Direct client-to-Supabase insert. No server validation. No confirmation email. Worker-mediated insert with server-side validation. Confirmation email via Resend.
Contact Form Client-side only or Supabase insert. No email delivery. Worker receives submission, stores in D1, sends email via Resend to admin and confirmation to user.
Error Handling Toast notifications from caught client-side exceptions. Same toast UI, but errors are more structured — Workers return typed error responses. Workflows provide durable retry for transient failures.
Offline / Network Failure Client-side operations fail silently or show generic error toasts. Same client behaviour, but server-side durability means in-flight AI operations complete even if the client disconnects (Workflow continues independently).
