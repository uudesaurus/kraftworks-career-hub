1. Executive Summary

Kraftworks Career Hub is a trade-focused career support platform designed to help skilled workers and trade graduates improve job readiness through resume feedback, interview preparation, educational resources, and future employer engagement workflows.

This document upgrades the existing proposal into a structured corporate-standard requirements baseline. It is intended to remove ambiguity, define clear backend responsibilities, and document how the current platform should behave operationally, functionally, and administratively.

1.1 Current Product Position

The currently implemented application is a web platform built with React and Supabase that provides public content pages, authenticated career tools, AI-assisted workflows, administrative review functions, and waitlist capture for both trade graduates and employers.

1.2 Primary Product Objectives

  • Increase job readiness for trade workers through actionable resume and interview support.
  • Create a controlled AI workflow where generated outputs are reviewed before end-user consumption when appropriate.
  • Capture early market demand from both candidates and employers prior to broader marketplace or career fair launch.
  • Maintain operational simplicity with a serverless backend, auditable data model, and clear role-based access boundaries.

2. Business Context and Product Vision

2.1 Problem Statement

Trade graduates and skilled workers often lack affordable, immediate, and trade-specific support when preparing for employment opportunities. General career platforms are usually not optimized for certification-heavy roles, field-specific expectations, or early-career trade workflows. Kraftworks Career Hub should become a trusted digital career readiness platform for the skilled trades, combining practical learning resources, lightweight AI assistance, and controlled administrative review to produce career guidance that is useful, relevant, and safe enough for public rollout.

6. Backend Architecture and Data Model

6.1 Architecture Philosophy: Why Serverless, Why Not a Traditional Server

The Kraftworks backend is designed as a fully serverless, edge-first architecture. This is a deliberate engineering and business decision, not a default. Understanding why this matters requires examining the alternatives and why they were rejected for this specific product context.

The Traditional Server Model and Why It Does Not Fit

A traditional backend would involve a persistent server process — typically a Node.js Express application, a Django service, or a Rails monolith — running continuously on a cloud VM or container (EC2, DigitalOcean Droplet, Railway, Render). This approach requires:

  • Always-on compute cost. A server runs 24/7 regardless of whether any user is making a request. For an early-stage product with unpredictable traffic, this means paying for idle capacity the majority of the time.
  • Infrastructure maintenance. Someone must manage OS patching, runtime version upgrades, SSL certificate renewal, load balancer configuration, health checks, and restart policies. This is operational overhead that directly competes with product development time.
  • Scaling complexity. When traffic spikes — for example, if a career fair drives 2,000 concurrent waitlist submissions — a traditional server would need auto-scaling groups, load balancers, and connection pooling to avoid collapsing. Each of these is a configuration surface area that introduces failure modes.
  • Cold-start irrelevance. The common argument against serverless is cold-start latency. For Kraftworks, no user-facing operation is latency-critical to the millisecond level. AI generation calls take 2-8 seconds regardless of infrastructure. A 50ms cold start on a Cloudflare Worker is imperceptible.

Why Serverless at the Edge

Cloudflare Workers execute on Cloudflare's global edge network — over 300 data centres worldwide. When a user in Houston submits a resume, the Worker that handles that request runs in the nearest Cloudflare point of presence, not in a single us-east-1 data centre thousands of miles away. This means:

  • Zero infrastructure management. There is no server to provision, patch, scale, or monitor. Cloudflare handles all of that. The engineering team writes functions, deploys them, and Cloudflare runs them globally.
  • Pay-per-invocation pricing. Cloudflare Workers are billed per request (first 100,000 requests/day free on the free tier, then $0.50 per million). For a beta product with hundreds of users, this means near-zero compute cost during low traffic, with automatic scaling to handle spikes without configuration changes.
  • Sub-millisecond cold starts. Unlike AWS Lambda (which can take 200ms-3s for cold starts depending on runtime), Cloudflare Workers use the V8 isolate model — the same engine that powers Chrome — which boots in under 5ms. There is no container to spin up, no runtime to initialise.
  • Built-in global distribution. Every Worker is automatically deployed to all 300+ edge locations. There is no CDN layer to configure separately. The function IS the edge.
  • Native integration with D1, R2, and Queues. Cloudflare's database (D1), object storage (R2), and message queue services are first-party integrations that work inside the same Worker runtime without external network hops.

Why This Matters for Kraftworks Specifically

Kraftworks is a career readiness platform for trade workers. The product value is in the AI-generated content (resume feedback, interview questions), the admin governance workflow, and the lead capture pipeline. None of these require a persistent, stateful server process. Every operation is a discrete request-response cycle: receive input, validate it, call an external AI service or write to a database, return a result. This maps perfectly to the serverless execution model. The team can focus entirely on product logic and AI quality rather than on infrastructure operations.

Architecture principle: Every backend responsibility in Kraftworks is implemented as a stateless, independently deployable function that runs at the network edge. There is no central server process, no container orchestration layer, and no infrastructure to manage. The system scales to zero when unused and scales to global capacity when needed, without human intervention.

6.3 How Everything Connects: The Request Lifecycle

Understanding the Kraftworks architecture requires tracing how a single request flows through every layer. Here is the complete path for the two core operations.

6.3.1 Resume Feedback Request Lifecycle

When a trade graduate clicks "Get Resume Feedback" on the Resume Review page, the following sequence executes:

  1. Client initiates. The React frontend calls the generate-resume-feedback Cloudflare Worker endpoint via an authenticated HTTP POST. The request includes the Clerk session JWT in the Authorization header and the resume_id in the request body.
  2. Edge receives. The request hits the nearest Cloudflare edge node. The Worker boots in under 5ms (V8 isolate cold start). The Clerk JWT is verified using Clerk's JWKS endpoint (cached at the edge after first fetch).
  3. Cloudflare Workflow begins. The Worker dispatches a durable Workflow instance. The Workflow is a multi-step sequence where each step is independently retryable. The Workflow ID is the user_id + resume_id combination, providing natural idempotency.
  4. Step 1 — Input Validation. The Workflow queries Cloudflare D1 to verify: (a) the resume_id exists and belongs to the authenticated user, (b) the user has not exceeded their AI quota (check ai_usage table, count records where user_id matches, reject if count ≥ 3), (c) the resume hash has not been processed before (deduplication check via SHA-256 hash in ai_usage.input_hash). If any check fails, the Workflow terminates with a user-readable error and no further steps execute.
  5. Step 2 — Context Enrichment. The Workflow fetches resume metadata from D1 (file_name, trade_program) and optionally retrieves the resume PDF from Cloudflare R2 for text extraction. The trade program field is mapped to domain-specific context using O*NET-aligned trade descriptors. This context string becomes part of the AI prompt.
  6. Step 3 — AI Inference via OpenRouter. The Workflow sends a structured request to OpenRouter's /api/v1/chat/completions endpoint. The request specifies the target model (e.g., google/gemini-2.5-flash or anthropic/claude-3.5-haiku), the system prompt (trade-aware career coach persona), the user prompt (resume context), and a forced function-call tool schema that constrains the output to the exact JSON structure required. OpenRouter routes the request to the selected model provider, handles rate limiting, and returns the structured response. If the model returns an error or times out, the Workflow retries this step up to 3 times with exponential backoff.
  7. Step 4 — Output Normalisation. The Workflow parses the tool-call JSON from the AI response. It validates that all required fields are present (overall_score, strengths, improvements, suggestions, trade_suggestions, actionable_steps). The score is clamped to the 1-10 range. Arrays are trimmed to expected cardinality. Malformed responses trigger a retry of Step 3 with a slightly modified prompt.
  8. Step 5 — Persistence. The Workflow writes two records to D1 in a single transaction: (a) the feedback record in resume_feedback with status = 'pending_review', and (b) the usage record in ai_usage with the action type, input hash, and timestamp. Because this is a Workflow step, if the write fails (D1 transient error), only this step retries — the AI call is not repeated.
  9. Step 6 — Admin Notification. The Workflow sends a transactional email via Resend to the admin notification address. The email includes the user's name, trade program, resume filename, and a direct link to the admin panel. If Resend is temporarily unavailable, the Workflow retries with backoff. The notification failure does not block the user response — the feedback record is already persisted.
  10. Response. The Workflow completes and the Worker returns a JSON response to the client indicating the feedback was generated and is pending review. The React frontend displays the "Pending Review" state. The user does NOT see the raw AI output until an admin approves it.

6.3.2 Interview Question Request Lifecycle

When a user pastes a job description and clicks "Generate Interview Questions":

  1. Client sends the job description text (truncated to 2,000 characters) and the resume_id to the generate-questions Worker endpoint with the Clerk JWT.
  2. Workflow Step 1 — Validation. Same quota and deduplication checks as the resume pipeline. Additionally validates that the job description meets the minimum length threshold (10 characters).
  3. Workflow Step 2 — Context Enrichment. Fetches resume metadata from D1. Builds a composite context string that combines the candidate's trade background with the target job description.
  4. Workflow Step 3 — AI Inference. Sends the structured request to OpenRouter with a prompt designed to generate categorised questions aligned to Bloom's Taxonomy levels: technical (Apply/Analyse), behavioural (Evaluate, STAR-formatted), and situational (Create/Evaluate). The tool-call schema forces the response into three string arrays.
  5. Workflow Step 4 — Normalisation and Persistence. Parses the response, validates array structure, writes the question set to interview_questions, and records AI usage in ai_usage. Both writes occur in a single D1 transaction.
  6. Response. Returns the generated questions directly to the client. Unlike resume feedback, interview questions do NOT pass through the admin approval gate — they are delivered immediately to the user. The rationale: interview questions are preparatory aids with low risk of harmful content, whereas resume scores directly affect user confidence and therefore require human review.

6.4 Why Each Service Was Chosen Over Alternatives

DecisionChosenAlternatives ConsideredRationale
Authentication Clerk Supabase Auth, Auth0, Firebase Auth, NextAuth Clerk provides pre-built UI components (sign-in/sign-up modals), user management dashboard, webhook-driven lifecycle events, and native Cloudflare Workers SDK. Supabase Auth ties the project to the Supabase ecosystem. Auth0 and Firebase are over-provisioned for this use case and introduce vendor lock-in to AWS/GCP infrastructure respectively. NextAuth is framework-specific to Next.js.
Database Cloudflare D1 Supabase PostgreSQL, PlanetScale, Turso, Neon D1 runs inside the same Cloudflare edge network as Workers, eliminating cross-network database roundtrips. For the current data model (7 tables, thousands of rows), SQLite's query engine is more than adequate. PostgreSQL features like JSON operators, full-text search, and advanced indexing are unnecessary for this workload. D1 avoids the connection pooling complexity that every serverless-to-PostgreSQL integration must solve (PgBouncer, Neon's pooler, Supabase's pooler).
Object Storage Cloudflare R2 AWS S3, Supabase Storage, Google Cloud Storage R2 is S3-compatible (same API) with zero egress fees. Resume PDFs are written once and read occasionally — the egress-free model eliminates unpredictable storage costs. R2 is accessed from Workers without leaving the Cloudflare network.
Serverless Functions Cloudflare Workers AWS Lambda, Supabase Edge Functions (Deno), Vercel Functions Workers provide sub-5ms cold starts (V8 isolates vs Lambda's 200ms-3s container boot). Workers are globally distributed by default (all 300+ Cloudflare locations) vs Lambda's single-region deployment. Workers' pricing (100K free requests/day) is the most competitive for a beta product. Supabase Edge Functions are Deno-based and locked to the Supabase ecosystem. Vercel Functions are tied to the Vercel deployment platform.
AI Provider OpenRouter Direct Anthropic API, Direct Google AI API, AWS Bedrock, Azure OpenAI OpenRouter provides a unified API endpoint that can route to any of 200+ models from multiple providers. This means model selection is a configuration change, not a code change. If Gemini's quality degrades or pricing changes, the system switches to Claude or Llama by changing a model string. Direct provider APIs create hard vendor dependencies. AWS Bedrock and Azure OpenAI require AWS/Azure accounts and VPC configuration.
Email Resend SendGrid, AWS SES, Postmark, Mailgun Resend provides a single-POST REST API callable from Workers. It supports React-based email templates (matching the frontend stack), includes delivery tracking, and handles SPF/DKIM/DMARC compliance. SendGrid and Mailgun have more complex setup and pricing. AWS SES requires AWS account infrastructure. Postmark is comparable but Resend's developer experience and pricing are optimised for early-stage products.

If the transaction fails, neither the output nor the usage is recorded — maintaining consistency. Prevents the failure mode where a user's quota is decremented but no output is produced, or where output is produced but the quota is not decremented (allowing infinite free usage).

6.8 Cloudflare Workflows: Why Durable Multi-Step Execution Matters

The AI pipelines are not simple request-response operations. They are multi-step workflows where each step can independently fail, and failure at step N should not repeat steps 1 through N-1. Cloudflare Workflows solve this problem with durable execution.

What Durable Execution Means in Practice

When a Cloudflare Workflow executes, each step is persisted to Cloudflare's infrastructure. If the Worker instance is recycled, the machine restarts, or the process crashes, the Workflow engine resumes execution from the last completed step — not from the beginning. This is fundamentally different from a single Worker function where a crash means starting over.

Why This Matters for AI Pipelines

  • AI calls are expensive and slow. An OpenRouter call to Gemini Flash takes 2-5 seconds and costs money. If the database write after the AI call fails (transient D1 error), a simple Worker would need to re-invoke the AI — doubling the cost and latency. A Workflow retries only the failed database step.
  • Email delivery is unreliable. Resend might be temporarily unavailable. In a simple Worker, this would either block the response (bad UX) or silently fail (admin never learns about the submission). A Workflow treats email as a separate step that retries independently without affecting the user response.
  • Partial state is dangerous. If the AI usage record is written but the feedback record is not (because the Worker crashed between two writes), the user loses a quota slot without receiving output. Workflows ensure step atomicity — either the persistence step completes fully, or it retries fully.

Workflow Configuration

7. AI Methodology and Pipeline Framework

This section documents the intellectual framework, prompt engineering methodology, and operational pipeline that govern how Kraftworks generates AI outputs. The goal is to ensure that every AI-generated artefact — whether a resume score, a set of interview questions, or a trade-specific suggestion — is produced through a systematic, research-grounded methodology that is consistent, auditable, and improvable over time.

7.1 Why a Methodology Matters

AI-generated content without a methodology is unpredictable. Two users with similar resumes might receive wildly different scores. Interview questions might be generic rather than trade-specific. Feedback might praise irrelevant capabilities while ignoring critical gaps. A methodology solves this by establishing:

  • Consistency. Every user receives output that follows the same evaluation criteria, scoring rubric, and question taxonomy — regardless of which LLM model processes their request.
  • Explainability. When a user asks "why did I get a 6/10?", the system can point to specific rubric anchors and competency dimensions rather than saying "the AI decided."
  • Improvability. Because the methodology is documented and modular, individual components (the rubric, the question taxonomy, the prompt structure) can be tested, measured, and improved independently.
  • Credibility. The methodology is grounded in established research from educational psychology, industrial-organisational psychology, and occupational classification — not ad hoc prompt engineering.

7.2 Foundational Research Frameworks

The Kraftworks AI system draws from the following established frameworks. Each framework maps to a specific component of the pipeline, not as abstract theory but as a concrete design input that shapes how the AI prompt is constructed, how output is structured, and how quality is evaluated.

FrameworkSourceApplication in Kraftworks
Bloom's Revised Taxonomy Anderson & Krathwohl (2001). A Taxonomy for Learning, Teaching, and Assessing. Interview question categorisation. Bloom's taxonomy classifies cognitive demand across six levels: Remember, Understand, Apply, Analyse, Evaluate, Create. Kraftworks maps its three question categories to specific Bloom's levels: Technical questions target Apply and Analyse (can the candidate apply trade knowledge to practical scenarios?). Behavioural questions target Evaluate (can the candidate assess their own past performance and decisions?). Situational questions target Create and Evaluate (can the candidate synthesise a response to a novel, hypothetical scenario?). This mapping is embedded in the system prompt as an instruction to the LLM, ensuring questions are calibrated to the appropriate cognitive demand — not randomly generated.
STAR Method Janz (1982) — initial structured interview research. Refined as an industry-standard behavioural interview technique. Behavioural question design. The STAR method (Situation, Task, Action, Result) is the gold standard for behavioural interview questions because it produces specific, evidence-based responses rather than hypothetical generalisations. The Kraftworks system prompt instructs the LLM to formulate behavioural questions that naturally elicit STAR-structured answers — for example, "Tell me about a time you identified a safety hazard on a jobsite. What was the situation, what did you do, and what was the result?" rather than a vague "How do you handle safety?"
Competency-Based Interview (CBI) Framework Campion, Palmer & Campion (1997). A review of structure in the selection interview. Personnel Psychology, 50(3). Job-description-to-competency mapping. CBI research demonstrates that interview effectiveness increases when questions are mapped to specific, job-relevant competencies rather than generic traits. The Kraftworks prompt pipeline takes the user's submitted job description and instructs the LLM to identify the implicit competency domains (technical skill, safety awareness, teamwork, problem-solving, tool proficiency, code compliance) before generating questions. This ensures that a job description for a commercial electrician produces different questions than one for a residential HVAC technician, even though both are "trades" roles.
O*NET Content Model US Department of Labor. Occupational Information Network — standardised descriptors for 1,000+ occupations. Trade-context enrichment. O*NET provides structured descriptions of the knowledge, skills, abilities, and work context for specific occupations — including electricians, HVAC mechanics, and welders. The Kraftworks system prompt incorporates O*NET-aligned language to ground the LLM in trade-specific expectations. For example, when generating feedback for a welder's resume, the prompt references O*NET descriptors for welding occupations: "blueprint reading, joint preparation, positional welding, AWS certification standards, safety equipment operation." This prevents the LLM from defaulting to generic corporate resume advice that is irrelevant to a trades professional.
NACE Career Readiness Competencies National Association of Colleges and Employers (2021 revision). Eight competencies: Critical Thinking, Communication, Teamwork, Technology, Leadership, Professionalism, Career & Self-Development, Equity & Inclusion. Resume scoring rubric dimensions. The resume feedback system evaluates resumes against observable signals that map to NACE competencies. A score of 8/10 requires evidence of multiple NACE competency signals: clear communication (resume structure and language), technology proficiency (tool and software literacy), professionalism (formatting, completeness), and career development awareness (certifications, continuing education). The scoring rubric anchors (Section 7.5) are calibrated against these competency dimensions.
Rubric-Anchored Evaluation Brookhart (2013). How to Create and Use Rubrics for Formative Assessment and Grading. Resume score consistency. Educational assessment research shows that human evaluators produce more consistent scores when they use rubrics with explicit anchors for each score level, rather than holistic impression scoring. The Kraftworks AI scoring prompt includes explicit descriptors for each score band (1-3 Weak, 4-6 Adequate, 7-9 Strong, 10 Exceptional) with concrete signals for each band. This reduces the variance in AI-generated scores across different prompts and models.
Human-in-the-Loop (HITL) Validation Amershi et al. (2019). Guidelines for Human-AI Interaction. CHI '19. Microsoft Research. Admin approval gate for resume feedback. Research on human-AI interaction establishes that AI systems producing consequential outputs (outputs that affect user decisions, confidence, or actions) should include a human verification step before delivery. Resume scores directly influence a trade worker's confidence and career decisions. The Kraftworks HITL model ensures that every AI-generated resume feedback passes through an admin reviewer who can approve, edit, or reject the output before the user sees it. This catches hallucinated feedback, inappropriate scores, and off-domain advice.
Chain-of-Thought Prompting Wei et al. (2022). Chain-of-Thought Prompting Elicits Reasoning in Large Language Models. NeurIPS 2022. Internal reasoning before output. Research shows that instructing LLMs to reason step-by-step before producing a final answer improves accuracy, especially for multi-dimensional evaluation tasks. The Kraftworks resume scoring prompt instructs the model to internally assess the resume against each rubric dimension before computing the final score — rather than generating a score first and then rationalising it. This is implemented as a thinking instruction in the system prompt, not as a visible output to the user.
Structured Output / Constrained Decoding Industry-standard pattern since OpenAI function-calling (2023). Adopted by Anthropic (tool use), Google (function calling), Meta (structured output). Deterministic output schema. Both Kraftworks pipelines use forced tool-call output with strict JSON schemas and additionalProperties: false. The LLM cannot return free-form text — it must produce a machine-parseable JSON object that matches the defined schema exactly. This eliminates the entire class of problems where AI output is "almost right but can't be reliably parsed" — a problem that plagues prompt-and-parse approaches.
Role-Anchored Prompting Shanahan et al. (2023). Role play with large language models. Nature, 623. Trade-specific persona grounding. Research on LLM role-play demonstrates that assigning an explicit persona ("You are a career coach specialising in skilled trades") measurably improves output relevance and reduces off-domain drift compared to generic instructions. Every Kraftworks prompt opens with a role declaration that anchors the model in the trades career coaching domain.

7.3 The Prompt Engineering Architecture: ICIO + Role-Anchoring

Every AI prompt in Kraftworks follows a four-layer architecture called ICIO (Instruction, Context, Input, Output), overlaid with Role-Anchoring. This is not a loose guideline — it is a structural template that every prompt must follow. Understanding each layer explains why the AI produces the outputs it does.

LayerPurposeImplementation in Resume FeedbackImplementation in Interview Questions
Role Anchor Establish the LLM's persona and domain expertise. Constrains the model's response space to trade-relevant career coaching. "You are a senior career coach specialising in skilled trades professionals (HVAC technicians, electricians, welders, plumbers, carpenters). You evaluate resumes against industry hiring standards for blue-collar and certification-heavy roles." "You are a senior career coach specialising in skilled trades. You prepare candidates for trade-specific interviews by generating questions that test practical knowledge, workplace behaviour, and adaptive problem-solving for field-based roles."
I — Instruction Define the task precisely, including output cardinality, tone, and evaluation criteria. "Analyse the submitted resume and provide structured feedback. Score on a 1-10 scale using the provided rubric anchors. Generate 3-4 bullet points per category. Each bullet should be concise (1-2 sentences), specific, and actionable. Do not use generic advice — reference the candidate's trade specialisation." "Generate 3-4 interview questions per category. Each question must be specific to the job description provided. Technical questions should test applied knowledge. Behavioural questions should elicit STAR-structured responses. Situational questions should present hypothetical trade scenarios."
C — Context Inject domain-specific grounding: trade vertical, resume metadata, candidate context. Dynamic: "The candidate specialises in [HVAC/Electrical/Welding]. Resume file: [filename.pdf]. O*NET reference: [trade-specific descriptors for the candidate's specialisation]." Dynamic: "The candidate has uploaded a resume: [filename.pdf]. The target job description follows. Identify the implicit competency domains (technical skill, safety, teamwork, tools, compliance) from the job description before generating questions."
I — Input The user-supplied content that the model must reason about. Resume metadata (file name, trade program). In v2: extracted resume text content. Job description text (truncated to 2,000 characters for cost and relevance control).
O — Output Strict structured schema enforced through OpenRouter's tool-calling / function-calling capability. Forced tool call: return_feedback with schema: { overall_score: integer, strengths: string[], improvements: string[], suggestions: string[], trade_suggestions: string[], actionable_steps: string[] }. additionalProperties: false. Model cannot deviate from this structure. Forced tool call: return_questions with schema: { technical: string[], behavioral: string[], situational: string[] }. additionalProperties: false.

Why ICIO Rather Than Free-Form Prompting

Free-form prompting (writing a long natural-language paragraph and hoping the AI follows it) produces inconsistent results because the model must simultaneously infer the task, the context, the format, and the constraints from unstructured text. ICIO separates these concerns into distinct layers, which means:

  • Each layer can be tested independently. If the scores are inconsistent, the problem is in the Instruction layer (rubric anchors) or the Output layer (schema constraints) — not in the Context or Input.
  • Each layer can be improved independently. Adding O*NET descriptors to the Context layer improves trade-relevance without changing the scoring Instruction. Adding Chain-of-Thought to the Instruction layer improves reasoning without changing the Output schema.
  • The architecture is model-portable. Because the prompt follows a standard structure, switching from Gemini to Claude or Llama requires zero prompt restructuring — only model-specific tuning of the Instruction layer (e.g., Claude responds better to XML-tagged instructions, Gemini responds better to numbered lists).

7.4 Pipeline 1: Resume Scoring and Feedback

The resume feedback pipeline is a six-stage durable workflow that transforms a raw PDF upload into structured, human-reviewed career feedback. Each stage is a discrete Cloudflare Workflow step with independent retry capability.

Stage 1 — Input Validation

The Workflow receives the resume_id and the authenticated user_id from the Clerk JWT. It performs three validation checks against Cloudflare D1:

  • Ownership check: SELECT from resumes WHERE id = resume_id AND user_id = authenticated_user_id. If no match, reject with "Resume not found."
  • Quota check: SELECT COUNT(*) from ai_usage WHERE user_id = authenticated_user_id. If count ≥ MAX_AI_ACTIONS, reject with "You have used all your AI actions for the beta period."
  • Deduplication check: Compute SHA-256 hash of "resume_feedback:" + resume_hash. SELECT from ai_usage WHERE input_hash = computed_hash. If found, reject with "You have already generated feedback for this resume version. Upload a new resume to generate new feedback."

If all three checks pass, the Workflow advances to Stage 2. If any check fails, the Workflow terminates immediately — no AI cost incurred, no database state changed.

Stage 2 — Context Enrichment

The Workflow fetches the resume record from D1 to extract file_name and trade_program. The trade program is mapped to an O*NET-aligned context string:

  • HVAC: "The candidate specialises in HVAC and refrigeration. Relevant industry expectations include: EPA 608 certification, refrigerant handling, system diagnostics, load calculations, ductwork design, preventive maintenance scheduling, ASHRAE standards awareness."
  • Electrical: "The candidate specialises in electrical technology. Relevant industry expectations include: NEC code compliance, conduit bending, circuit analysis, motor controls, PLC fundamentals, lockout/tagout procedures, journeyman or master electrician licensure."
  • Welding: "The candidate specialises in welding technology. Relevant industry expectations include: AWS certification (D1.1 structural, D1.2 aluminium), blueprint reading, joint preparation, positional welding (all positions), MIG/TIG/stick processes, metallurgy basics, weld inspection."

In v2, this stage will also retrieve the resume PDF from R2 and extract text content using a PDF parsing library, providing the LLM with the actual resume text rather than just metadata.

Stage 3 — AI Inference via OpenRouter

The Workflow sends a structured request to OpenRouter's chat completions endpoint. The request is constructed as follows:

  • Endpoint: https://openrouter.ai/api/v1/chat/completions
  • Model selection: Configured via Worker environment variable. Default: google/gemini-2.5-flash for cost efficiency ($0.15/1M input tokens). Fallback: anthropic/claude-3.5-haiku ($0.80/1M input). Premium option: anthropic/claude-sonnet-4 ($3.00/1M input) for cases requiring higher analytical depth.
  • System message: Contains the Role Anchor + Instruction + Context layers from the ICIO architecture.
  • User message: Contains the Input layer — resume metadata and (in v2) extracted resume text.
  • Tool definition: The return_feedback function with strict schema.
  • Tool choice: { "type": "function", "function": { "name": "return_feedback" } } — forcing the model to use the structured output tool.
  • Temperature: 0.3 — low enough for scoring consistency, high enough to avoid repetitive language across different resumes.

If OpenRouter returns a 429 (rate limit), the Workflow step retries with exponential backoff. If OpenRouter returns a 5xx error, the step retries up to 3 times. If all retries fail, the Workflow terminates with a user-readable error and no database state is changed.

Stage 4 — Output Normalisation

The Workflow parses the tool_calls[0].function.arguments JSON string from the AI response. It performs the following normalisations:

  • Score clamping: overall_score is clamped to the integer range [1, 10]. Values outside this range are adjusted to the nearest boundary.
  • Array validation: Each array field (strengths, improvements, suggestions, trade_suggestions, actionable_steps) is verified to be a non-empty array of strings. Empty arrays trigger a retry of Stage 3.
  • Content sanitisation: String values are trimmed of leading/trailing whitespace, and any embedded HTML or markdown formatting is stripped to ensure clean display in the frontend.

Stage 5 — Persistence

The Workflow executes a D1 transaction that atomically writes two records:

  • resume_feedback record: All normalised fields plus status = 'pending_review', user_id, resume_id, resume_hash, and created_at.
  • ai_usage record: user_id, action_type = 'resume_feedback', input_hash (the SHA-256 deduplication key), workflow_id, and created_at.

Because these two writes are in a single D1 transaction, either both succeed or neither does. This prevents the failure mode where quota is consumed but no feedback is stored, or where feedback is stored but quota is not recorded (allowing unlimited free usage).

Stage 6 — Admin Notification via Resend

The Workflow sends a transactional email to the admin notification address via Resend's REST API:

  • Recipient: Admin email address (configured as Worker environment variable).
  • Subject: "New Resume Feedback Pending Review — [User Name]"
  • Body: User name, email, trade program, resume filename, submission timestamp, and a direct link to the admin panel feedback tab.
  • Failure handling: Notification failure does not block the user response. The feedback record is already persisted. If Resend is unavailable, the step retries up to 3 times, then logs the failure for operational review.

7.6 Pipeline 2: Interview Question Generation

The interview question pipeline is a five-stage Cloudflare Workflow that transforms a job description into categorised, trade-relevant interview preparation questions.

Stage 1 — Input Validation

Same authentication, quota, and deduplication checks as the resume pipeline. Additionally validates that the job description meets the minimum length threshold (10 characters) and truncates to 2,000 characters for cost control and prompt relevance.

Stage 2 — Context Enrichment

Fetches resume metadata from D1 if a resume_id is provided. Builds a composite context string that combines the candidate's trade background with the target job description. The prompt instructs the LLM to perform implicit competency mapping: identify the job's required competencies (technical skill, safety awareness, teamwork, tool proficiency, code compliance) before generating questions.

Stage 3 — AI Inference via OpenRouter

The request is structured identically to the resume pipeline but with a different system prompt, user prompt, and tool schema. Key differences:

  • Model: Default google/gemini-2.5-flash. Question generation is less analytically demanding than resume scoring, so the cost-efficient model is preferred.
  • Temperature: 0.5 — slightly higher than resume scoring to encourage varied question phrasing across multiple generations.
  • Tool schema: return_questions with { technical: string[], behavioral: string[], situational: string[] }.
  • Bloom's alignment instruction: The system prompt explicitly instructs: "Technical questions should test at the Apply and Analyse levels of Bloom's Taxonomy. Behavioural questions should target the Evaluate level and be structured to elicit STAR-method responses. Situational questions should target Create and Evaluate levels with hypothetical trade-specific scenarios."

Stage 4 — Normalisation and Persistence

Parses the tool-call response, validates that all three arrays are present and non-empty, writes the question set to interview_questions, and records AI usage in ai_usage — both in a single D1 transaction.

Stage 5 — Response

Returns the generated questions directly to the client. Interview questions do NOT pass through the admin approval gate. The rationale: questions are preparatory aids that help users practice. They do not carry the same risk as resume scores (which directly affect confidence and career decisions). The cost of false negatives (blocking a useful question behind a review queue) outweighs the risk of false positives (a slightly imperfect question reaching the user).

7.10 Model Selection Strategy and Future Roadmap

OpenRouter's model-agnostic architecture means model selection is a configuration decision, not an engineering decision. The current selection criteria and future evolution path:

CriterionCurrent ApproachFuture Approach
Default Model google/gemini-2.5-flash — cost-optimised for beta traffic volumes. A/B test across Gemini, Claude Haiku, and Llama 4 to measure output quality per dollar across each pipeline.
Fallback Strategy Single fallback model (anthropic/claude-3.5-haiku) on primary failure. Cascading fallback: primary → secondary → tertiary. Automatic routing via OpenRouter's provider preferences parameter.
Quality Measurement Admin review acts as a manual quality gate for resume feedback. Introduce an offline evaluation set (gold-standard scored resumes) to measure prompt quality regression across model and prompt changes.
Resume Text Extraction Only file metadata available. The model evaluates based on trade context and metadata, not resume content. Extract full resume text from PDF (via a lightweight PDF parser running in the Worker or as a pre-processing step) and pass the text as the Input layer. This is the single highest-impact improvement for feedback quality.
Few-Shot Exemplars Zero-shot prompting (no examples in the prompt). Include 1-2 gold-standard resume evaluations in the system prompt as few-shot exemplars (Brown et al., 2020). This has been shown to significantly improve output consistency.
Self-Refinement Single-pass inference. Two-pass inference: first pass generates output, second pass critiques and refines it (Madaan et al., 2023 — Self-Refine). Doubles inference cost but substantially improves accuracy for scoring tasks.

9. Security, Privacy, and Governance

9.1 Access Control

  • Protected routes must require authentication.
  • Administrative workflows must require explicit admin role assignment.
  • Backend data access must be constrained by row-level security policies wherever appropriate.

9.2 Data Sensitivity

  • Resume files and associated feedback are user-sensitive data and must not be publicly exposed.
  • Waitlist submissions contain personal and business contact data and must be treated as controlled internal data.
  • Job descriptions entered by users may contain employer-sensitive details and should be handled as private user input.

9.3 Governance Requirements

AreaRequirement
AI Output GovernanceResume feedback shall pass through admin review before approved content is exposed to users.
Legal VisibilityPrivacy policy and terms of service pages must remain public and accessible.
Operational LoggingEdge functions and admin actions should be observable enough for troubleshooting and support.
Change ManagementSchema, role, and AI prompt changes should be version-controlled and released intentionally.

10. Delivery Assumptions, Risks, and Out of Scope

10.1 Delivery Assumptions

  • Supabase remains the authoritative backend platform for auth, database, storage, and edge functions.
  • Existing route structure and product positioning remain substantially unchanged during this documentation baseline period.
  • AI provider behavior and model availability may change over time, but structured output contracts remain mandatory.
  • Admin review remains part of the quality-control model for resume feedback.

10.2 Key Risks

  • Current resume feedback quality is limited by the absence of full resume text extraction and deeper parsing.
  • Email notification workflow is not yet production-complete, which creates operational visibility gaps.
  • AI quota is deliberately small and may constrain user value if beta usage grows before policy changes are introduced.
  • Employer functionality is currently demand-capture only, which may create expectation gaps if not communicated clearly.

10.3 Explicit Out-of-Scope Items

  • Real-time chat or messaging between employers and candidates.
  • Payment collection, invoicing, or subscription billing.
  • Automated hiring workflow or applicant tracking system capability.
  • Advanced analytics dashboards beyond current lightweight summaries and CSV export patterns.
