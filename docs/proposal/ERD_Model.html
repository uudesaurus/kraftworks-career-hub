Kraftworks Career Hub — ERD Model and Data Interaction Reference

Standalone entity relationship and data lifecycle document for the proposed Clerk + Cloudflare + OpenRouter + Resend architecture

This document is intentionally diagram-free. It expresses the ERD as a rigorous narrative data model, including entities, keys, constraints, lifecycle relationships, and integration boundaries.

Purpose. This document defines the canonical data model for the proposed backend. It explains which records exist, why they exist, which services own them, how they relate to one another, and how data moves across authentication, storage, AI pipelines, admin review, waitlist capture, and email delivery.

1. Modeling Scope

The proposed backend architecture splits the overall system into five data domains. Thinking in these domains makes the ERD easier to reason about than treating every record as a flat table list.

Domain Responsibility Primary System Persistence Type
Identity User authentication, session issuance, external source of truth for account identity. Clerk External managed identity service
Operational Core User records, resumes, feedback, interview questions, roles, quota tracking. Cloudflare D1 Relational tables
File Storage Resume PDF binaries and storage metadata references. Cloudflare R2 Object storage
AI Execution Inference requests and structured outputs generated by LLMs. OpenRouter via Cloudflare Workflows Ephemeral execution + durable result persistence in D1
Communications Admin notifications, user confirmations, operational email flows. Resend External delivery system with optional mirrored records in D1

2. Current-to-Proposed Data Baseline

The current codebase uses Supabase PostgreSQL and already has a mature shape. The proposed model preserves that product logic but relocates ownership from Supabase to Clerk, Cloudflare D1, R2, Workflows, and Resend.

6. Referential and Lifecycle Rules

The most important part of an ERD is not the foreign keys alone. It is the lifecycle policy behind them: what gets deleted, what gets preserved, and what should be immutable after creation.

Entity Delete Policy Update Policy Reasoning
usersSoft delete recommendedSync from Clerk webhookUser-linked records should not become orphaned or vanish from audit history.
resumesPrefer deactivate over hard deleteMetadata mutable, hash immutable per versionFeedback and questions may reference historical resume versions.
resume_feedbackDo not hard delete except administrative purgeEditable only by admin review flowIt is part of the trust and audit model.
interview_questionsRetain unless retention policy says otherwiseImmutable after generationActs as historical prep record and reuseable user history.
ai_usageRetainImmutableNeeded for cost tracking, abuse detection, and dispute resolution.
user_rolesRetain historical rows or deactivateRole changes append-preferredRole history can matter in governance investigations.
waitlist tablesRetain until consent or data retention policy requires purgeRarely updatedThese are marketing and go-to-market records.
admin_audit_logNever delete under normal operationImmutableAudit history loses meaning if it can be edited.

Critical governance point. Resume feedback should never be overwritten in place without preserving review history. If an admin materially edits a machine-generated record, the system should either record a delta in admin_audit_log or store an edited revision snapshot. Otherwise the platform cannot later explain what the AI originally produced versus what the human reviewer changed.

7. Interaction Model by Capability

7.1 Authentication and User Sync

  1. Clerk creates or updates the user.
  2. A Clerk webhook hits a Cloudflare Worker.
  3. The Worker upserts the users table in D1.
  4. If role mapping exists, the Worker also upserts user_roles.
  5. Frontend requests use Clerk JWTs, but Workers query D1 for authorisation and user-linked data.

7.2 Resume Upload

  1. User uploads a PDF.
  2. Worker validates file type and size, then writes the object to R2.
  3. Worker computes the file hash and writes metadata into resumes.
  4. Any previous active resume for the same user is deactivated or superseded.
  5. The frontend now references the D1 metadata record, not the raw storage object.

7.3 Resume Feedback Generation

  1. The user triggers the feedback flow.
  2. Worker or Workflow validates the user, resume ownership, quota, and deduplication using users, resumes, and ai_usage.
  3. The Workflow optionally reads the PDF from R2 for text extraction.
  4. OpenRouter is called with the structured prompt and model selection.
  5. The output is normalised and persisted into resume_feedback with status = 'pending_review'.
  6. A paired record is written into ai_usage.
  7. Resend sends an admin notification.
  8. Admin review later updates the status to approved or rejected.

7.4 Interview Question Generation

  1. The user submits a job description.
  2. Worker validates quota and input uniqueness through ai_usage.
  3. Optional resume context is loaded from resumes.
  4. OpenRouter returns structured question arrays.
  5. The result is written to interview_questions.
  6. The usage event is written to ai_usage.
  7. The user sees the result immediately.

7.5 Admin Review and Operations

  1. Admin opens the panel with a valid Clerk session.
  2. Worker verifies the admin role using user_roles.
  3. Admin queries feedback, waitlists, and optionally contact submissions from D1.
  4. Approval, rejection, edit, and export actions write an admin_audit_log row.
  5. Feedback review updates resume_feedback.status and review metadata.

7.6 Public Waitlist and Contact Capture

  1. Unauthenticated visitor submits a trade graduate waitlist, employer waitlist, or contact form.
  2. Worker validates the payload and writes the corresponding D1 row.
  3. Resend optionally sends confirmation and internal notification emails.
  4. Optional webhook events mirror delivery status into email_events.

8. External System Boundaries

The ERD is not complete unless the off-database boundaries are explicit. Several critical data objects live outside D1 and must be treated as first-class dependencies.

External System Owns What How D1 References It Risk if Unsynchronised
Clerk Identity, email verification state, active sessions users.id mirrors Clerk user ID User exists in Clerk but not in D1, causing broken joins or missing dashboard state
Cloudflare R2 Resume PDF binaries resumes.file_path Metadata exists but file object is missing, breaking feedback generation
OpenRouter Inference runtime and model routing resume_feedback.model_name, interview_questions.model_name, ai_usage.model_name Impossible to explain model provenance, debug quality issues, or analyse cost
Resend Email delivery execution Optional email_events.external_message_id No operational visibility into whether notifications actually delivered
Cloudflare Workflows Durable multi-step execution state workflow_id columns across AI-linked tables Harder debugging of retries, partial failures, or duplicate requests

9. Recommended Constraints and Indexes

A data model without access patterns is incomplete. These indexes and constraints support the actual product workflows described in the proposal.

Entity Index / Constraint Why It Matters
usersUnique index on emailPrevents duplicate mirrored identity rows.

resumesIndex on user_id, unique index on file_path, index on file_hashFast dashboard lookup and dedupe.

ai_usageIndex on user_id, unique or constrained lookup on action_type + input_hash per userQuota checks and deduplication performance.

employer_waitlistIndex on company_email, index on created_atLead review and commercial prioritisation.

10. Final ERD Position

The proposed ERD is intentionally conservative. It does not over-engineer the system with marketplace entities, employer workspaces, applicant pipelines, or billing objects that do not yet exist in the product. Instead it supports exactly what the product is trying to do now:

  • Authenticate and recognise users cleanly through Clerk.
  • Store resume metadata in D1 and resume files in R2.
  • Run AI workflows durably through Cloudflare Workers and Workflows.
  • Persist AI outputs with governance-aware lifecycle controls.
  • Track quota, dedupe, and operational accountability.
  • Capture public demand from candidates and employers.
  • Add enough operational tables to avoid blind spots in contact handling, review auditing, and email visibility.

Recommendation. Treat this document as the canonical schema design reference for the migration from Supabase to Clerk + Cloudflare. If the backend scope expands later into employer workspaces, candidate profiles, career fair event execution, or analytics, those should be added as a second-phase ERD extension rather than mixed into the launch schema.
